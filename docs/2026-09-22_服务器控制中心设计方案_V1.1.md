# 诗影工坊（PoemVideo Studio）服务器控制中心设计方案 V1.1

> 项目仓库：`hjp1137/poem-video-studio`  
> 模块名称：服务器控制中心（Server Control Center）  
> 文档版本：V1.1  
> 日期：2026-09-22

## 1. 背景

PoemVideo Studio V1.0 主要解决“整首诗一次输入、批量提交 MiniMax H3 / ComfyUI 视频任务”的生产效率问题。

当前本地 GPU 服务器在实际使用中仍存在大量需要 SSH 手工执行的运维动作，例如：

1. 查看 4 张 RTX 4090 的运行状态。
2. 设置 GPU Power Limit。
3. 查看和关闭占用 GPU 的模型服务。
4. 启动 / 停止 / 重启 MiniMax H3。
5. 启动 / 停止 / 重启 ComfyUI。
6. 在准备视频生成环境前，人工判断模型是否冲突、GPU 是否可用。

这些动作与 PoemVideo Studio 的视频生产流程高度相关，因此 V1.1 增加“服务器控制中心”，把高频且明确的服务器操作收敛到 Web 页面中。

目标不是把 PoemVideo Studio 变成通用 Linux 运维平台，而是建立一个**面向本地 AI 视频生产场景的受控运维面板**。

## 2. 核心目标

V1.1 服务器控制中心需要实现：

- GPU 状态监控
- GPU 功耗限制查看与修改
- 已登记模型/服务状态查看
- 已登记模型/服务启动、停止、重启
- MiniMax H3 专项控制
- ComfyUI 专项控制
- 视频环境“一键准备”
- 操作日志与错误追踪
- 严格白名单，不开放任意 Shell

## 3. 非目标

V1.1 明确不实现：

- 浏览器任意 Shell / Terminal
- 任意进程 kill
- 任意 systemctl 服务控制
- 任意 Docker 容器控制
- 操作系统用户管理
- 磁盘分区
- 防火墙配置
- BIOS / BMC 配置
- NVIDIA 驱动安装升级
- 内核升级

这些功能超出诗词视频生产工具的职责边界。

## 5. 为什么需要 Host Agent

PoemVideo Studio API 建议继续以 Docker 容器运行。

直接给 Web/API 容器：

- root
- `--privileged`
- Docker socket
- unrestricted sudo
- 任意 shell

都会扩大攻击面。

因此引入 `poem-video-agent`：

- 运行在 Ubuntu 宿主机。
- 默认监听 `127.0.0.1` 或仅内部网络。
- 只提供明确白名单 API。
- 所有高权限操作均通过固定动作执行。
- 不接收任意 shell command 字符串。

## 6. GPU 状态管理

### 6.1 状态字段

每张 GPU 卡至少展示：

- GPU Index
- GPU Name
- Temperature
- GPU Utilization
- Memory Used
- Memory Total
- Power Draw
- Power Limit
- Fan Speed（驱动支持时）
- P-State
- Running Processes

推荐通过：

```bash
nvidia-smi --query-gpu=index,name,temperature.gpu,utilization.gpu,memory.used,memory.total,power.draw,power.limit,pstate --format=csv,noheader,nounits
```

获取基础数据。

进程通过 `nvidia-smi` GPU process query 或 XML / structured parser 获取。

不得依赖对人类格式 `nvidia-smi` 输出做脆弱的字符串切割。

### 6.2 前端展示

建议一张 GPU 一张卡片：

```text
GPU 0 · RTX 4090
温度        66℃
GPU利用率    82%
显存        21.3 / 24 GB
当前功耗     266W
功耗上限     280W
P-State     P2

进程：
PID 12345  python  20134 MiB
```

顶部增加总体摘要：

```text
GPU：4/4 正常
总显存：96 GB
已用显存：xx GB
最高温度：xx℃
```

### 6.3 刷新策略

默认：

- 页面可见时每 3～5 秒刷新一次。
- 页面不可见时降低刷新频率。
- 允许手动刷新。
- GPU 查询失败不影响其他服务器管理功能。

## 7. GPU 功耗限制

### 7.1 功能

支持：

- 查看每卡当前 Power Limit。
- 单卡设置。
- 全部 GPU 同时设置。
- 设置默认功耗值。
- 可配置“服务器启动后自动应用”。

例如：

```text
GPU0 [280 W]
GPU1 [280 W]
GPU2 [280 W]
GPU3 [280 W]

[全部设为 280W]
```

### 7.2 安全范围

Agent 必须读取 GPU 支持的 min/max power limit。

用户提交值必须满足：

```text
min_power_limit <= requested <= max_power_limit
```

不允许前端自行假定 4090 的固定区间。

### 7.3 实际执行

允许动作仅为类似：

```bash
nvidia-smi -i <index> -pl <watts>
```

Agent 内部构造参数，API 不接收原始命令。

### 7.4 开机自动应用

推荐使用 systemd oneshot：

```text
poem-video-gpu-power.service
```

读取：

```text
/etc/poem-video-agent/gpu-power.json
```

例如：

```json
{
  "enabled": true,
  "default_power_limit": 280,
  "per_gpu": {}
}
```

这样服务器重启后无需人工再次执行。

## 8. 服务注册模型

只允许控制已登记服务。

配置文件建议：

```yaml
services:
  minimax_h3:
    display_name: "MiniMax H3"
    manager: systemd
    unit: "minimax-h3.service"
    health:
      type: http
      url: "http://127.0.0.1:<PORT>/health"
    gpu_profile: "h3"

  comfyui:
    display_name: "ComfyUI"
    manager: systemd
    unit: "comfyui.service"
    health:
      type: http
      url: "http://127.0.0.1:8188/"

  ollama:
    display_name: "Ollama"
    manager: systemd
    unit: "ollama.service"
    health:
      type: http
      url: "http://127.0.0.1:11434/api/tags"
```

如果现有服务通过 Docker 管理，可以扩展：

```yaml
manager: docker
container: "xxx"
```

但 V1.1 优先建议将 MiniMax H3 与 ComfyUI 规范化为 systemd 服务。

## 9. MiniMax H3 服务化

当前已验证可用的 H3 启动命令必须原样迁移进 systemd Unit，不重新设计推理参数。

建议：

```text
/etc/systemd/system/minimax-h3.service
```

要求：

- 固定 WorkingDirectory。
- 固定 Python/venv 路径。
- 固定模型路径。
- 固定 CUDA_VISIBLE_DEVICES / GPU 参数。
- 启动日志进入 journald。
- 正常 SIGTERM 停止。
- 设置合理的 TimeoutStopSec。
- 失败时可查看明确日志。
- 是否 Restart=on-failure 根据真实运行情况决定。

PoemVideo Studio 页面只执行：

```text
start
stop
restart
status
logs
```

不直接拼装 vLLM 命令。

## 10. ComfyUI 服务化

同理，将当前成功启动 ComfyUI 的命令规范化为：

```text
comfyui.service
```

页面展示：

- Running / Stopped / Failed
- PID
- Uptime
- HTTP Health
- Queue Pending
- Queue Running
- “打开 ComfyUI”链接
- Start / Stop / Restart

## 11. 服务停止策略

“关闭正在运行的一些模型”不能实现成“扫描进程后 kill”。

应分成两类：

### 11.1 已登记服务

例如：

- Ollama
- MiniMax H3
- ComfyUI

允许 Stop / Restart。

### 11.2 未登记 GPU 进程

只展示：

```text
PID
进程名
GPU
显存
用户
```

默认只读，不提供 kill。

如未来确实需要结束未知 GPU 进程，应新增单独设计与二次确认机制，不纳入 V1.1。

## 12. 一键准备视频环境

这是服务器控制中心最重要的生产入口。

按钮：

```text
[准备 MiniMax H3 视频环境]
```

建议流程：

```text
1. 检查 Agent
2. 检查 NVIDIA Driver / 4 GPU
3. 应用配置的 GPU Power Limit
4. 读取 GPU 当前进程
5. 检查是否存在已登记冲突服务
6. 根据环境 Profile 停止冲突服务
7. 启动 MiniMax H3
8. 等待 H3 Ready
9. 启动 ComfyUI
10. 等待 ComfyUI HTTP Ready
11. 检查 ComfyUI Queue API
12. 返回 READY
```

### 12.1 环境 Profile

建议配置：

```yaml
profiles:
  h3_video:
    power_limit: 280
    stop_services:
      - ollama
    start_services:
      - minimax_h3
      - comfyui
    health_timeout_seconds: 180
```

实际是否停止 Ollama、使用哪些 GPU，必须以当前服务器真实部署策略配置，不在代码中写死。

### 12.2 幂等性

“一键准备”必须可重复点击：

- 已经停止的服务不报错。
- 已经运行且健康的 H3 不重复启动。
- 已运行但不健康时允许 Restart。
- Power Limit 已经正确时不重复设置也可。
- ComfyUI 已运行时只做健康检查。

## 15. 权限与安全

### 15.1 Agent 监听

优先：

```text
127.0.0.1:<agent-port>
```

如果 API 在 Docker 内访问 Agent，则使用：

- host-gateway
- Unix Socket
- 或专门内部网络

不得直接暴露公网。

### 15.2 sudoers

Agent 运行用户只获得最小权限，例如允许：

- `/usr/bin/nvidia-smi`
- `systemctl start/stop/restart/status minimax-h3.service`
- `systemctl start/stop/restart/status comfyui.service`
- 被明确登记的其他 unit

不允许：

```text
ALL=(ALL) NOPASSWD: ALL
```

### 15.3 请求保护

所有修改型请求必须：

- 后端校验。
- Service name 必须来自注册表。
- GPU index 必须来自实际 GPU 列表。
- Power Limit 必须在驱动返回范围内。
- 日志接口限制最大行数。
- 操作落审计日志。

## 16. 状态与健康判定

服务状态拆为两层：

```text
process_state:
running / stopped / failed

health_state:
healthy / unhealthy / unknown
```

例如 systemd 显示 active，但 H3 HTTP 未 Ready，则页面应显示：

```text
Running / Starting
```

而不能直接显示 Ready。

## 17. 与视频生成流程联动

在 PoemVideo Studio 批量任务页面增加环境状态：

```text
MiniMax H3：Healthy
ComfyUI：Healthy
GPU：Ready

[开始生成]
```

如果环境未 Ready：

```text
视频生成环境未就绪
[一键准备环境]
```

但不应在用户创建 Batch 时自动关闭服务或修改 GPU 功耗。

高影响操作必须由用户明确点击。

## 22. 最终原则

PoemVideo Studio 的服务器控制中心遵循：

> **功能可以自动化，但权限不能泛化。**

只把已经明确、稳定、可审计的 GPU 与模型服务操作做成按钮，不把 Web 平台变成一个远程 root shell。
