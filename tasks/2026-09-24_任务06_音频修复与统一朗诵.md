# 2026-09-24 任务06：音频修复与统一朗诵

## 1. 任务目标

为 PoemVideo Studio 增加“音频修复 / 统一朗诵”能力。

解决 MiniMax H3 已生成视频中常见的音频问题：

- 诗句被唱出来，而不是朗诵。
- 同一首诗不同分段音色不一致。
- 部分分段朗诵语调机械、情绪不足。
- H3 视频画面已经满意，但仅因声音问题不得不重新生成整段视频。
- 需要保留原视频中的古风背景音乐、江水、秋风等环境声，只替换问题人声。

本任务的核心原则：

> 视频画面不重新生成；优先复用已生成的 H3 成品，只修复音频。

以《暮江吟》本轮 5 个成品视频作为首个验收样本，其中后两段音色作为优先参考音色，将出现唱腔的分段修复为自然普通话朗诵。

---

## 2. 用户操作目标

在 PoemVideo Studio 中新增一级功能：

```text
音频修复 / 统一朗诵
```

用户应能够完成以下流程：

```text
选择/上传 H3 成品视频
        ↓
选择一个“音色良好”的视频片段作为参考
        ↓
自动提取参考人声
        ↓
为每个待修复视频填写/确认正确诗句
        ↓
使用统一参考音色重新生成朗诵
        ↓
保留原 BGM / 环境声
        ↓
预听新旧效果
        ↓
输出修复后的 MP4
```

整个过程不需要重新运行 MiniMax H3。

---

## 3. V1 实施边界

本任务先实现可稳定使用的 V1，不做过度自动化。

### V1 必须实现

1. 支持 MP4 输入。
2. 从指定参考视频中提取音频。
3. 分离“人声”和“背景音乐/环境声”。
4. 从参考人声生成可用于声音克隆的参考片段。
5. 使用本地中文 TTS / 零样本声音克隆重新生成目标诗句。
6. 新朗诵必须为普通话“说话/朗诵”，禁止唱腔。
7. 将新朗诵与原 BGM / 环境声重新混合。
8. 保持原视频编码画面不变，尽量直接 copy video stream。
9. 支持批量修复多段视频。
10. 输出修复后的 MP4，并保留原始文件。

### V1 暂不强制

- 自动判断哪一段在唱。
- 自动识别所有诗句。
- 自动判断哪一个参考音色最好。
- 多角色配音。
- 大规模声音模型训练。
- 对原视频进行画面二次生成。

这些可以放到 V1.1 / V2。

## 4. 推荐技术路线

建议采用本地离线流水线：

```text
FFmpeg
  ↓
Demucs / UVR
  ↓
参考人声清理
  ↓
中文零样本 TTS / Voice Clone
  ↓
FFmpeg 混音
  ↓
FFmpeg Remux
```

### 4.1 FFmpeg

职责：

- MP4 提取音轨。
- 音频格式转换。
- 新旧音轨混音。
- 响度标准化。
- 将修复音频重新封装回原视频。
- 尽量使用：

```bash
-c:v copy
```

避免视频重新编码，保证：

- 原画质不下降。
- 处理速度快。
- 不再次消耗 H3 视频生成资源。

### 4.2 人声分离

优先支持：

- Demucs

同时预留：

- UVR / MDX 系模型

接口层不要与单一模型强耦合。

统一抽象：

```python
separate_audio(input_audio) -> {
    "vocals": "...",
    "accompaniment": "..."
}
```

V1 先保证：

- 人声提取足够清楚。
- 伴奏中尽量减少原朗诵残留。
- 古风背景音乐和环境声不被明显破坏。

### 4.3 中文朗诵生成

实现统一的 TTS Provider 接口：

```python
synthesize(
    text,
    reference_audio,
    reference_text=None,
    style="poetry_recitation"
) -> output_audio
```

首选接入一个本地中文零样本声音克隆方案。

推荐优先评估：

1. CosyVoice 系
2. GPT-SoVITS

选择标准不是“功能最多”，而是：

- 中文自然度。
- 零样本音色保持能力。
- 普通话稳定性。
- 能明确生成说话/朗诵而不是唱歌。
- 4090 上部署简单。
- 推理速度满足 5–10 秒短诗句批量处理。
- 可本地运行。

最终 Provider 选型必须经过实际 A/B 测试后确定。

禁止在业务代码中把项目锁死到单一 TTS 模型。

## 5. 参考音色机制

### 5.1 参考音色来源

允许用户从本次项目中的任意已生成视频选择：

```text
“使用此段音色作为整首诗参考”
```

系统自动：

1. 提取该视频音轨。
2. 分离人声。
3. 裁切有效人声区域。
4. 生成 reference.wav。
5. 保存为当前作品的 Voice Reference。

### 5.2 参考片段要求

推荐有效语音：

- 3–15 秒。
- 清晰。
- 尽量无重叠声音。
- 无明显唱腔。
- 无爆音。
- 情绪自然。
- 背景残留尽量少。

如果视频内 BGM 较强，先分离后再作为参考。

### 5.3 项目级音色

数据结构预留：

```text
project/
  voice/
    reference.wav
    reference.json
```

reference.json 示例：

```json
{
  "source_video": "ComfyUI_00065_.mp4",
  "provider": "cosyvoice",
  "created_at": "...",
  "note": "暮江吟后两段优选男声音色"
}
```

同一首诗的多个分段默认复用同一 Voice Reference。

## 6. “禁止唱腔”的朗诵控制

当前问题的关键不是简单换声音，而是保证输出始终是朗诵。

统一增加诗词朗诵 Style Preset：

```text
poetry_recitation
```

其目标描述：

```text
成年男性普通话，自然朗诵。
声音温润、沉静、富有诗意。
使用正常说话式发声，不演唱，不吟唱，不拖长尾音。
有适度情绪起伏，但不要舞台化。
按语义自然停顿，诗句只读一遍。
```

如果具体 TTS Provider 支持：

- instruct
- prompt text
- style
- speed
- emotion
- prosody

则由 Adapter 映射，不直接暴露到底层页面。

### 默认参数目标

- speed：接近正常朗诵，约 0.90–1.00 倍。
- pitch：不做明显升降调处理。
- 情绪：温润 / 平静 / 轻抒情。
- 禁止 singing / chant。
- 每句只读一次。
- 句尾自然收声。

## 7. 音频处理流程

单段视频标准流程：

```text
input.mp4
  │
  ├─ ① ffmpeg 提取 audio.wav
  │
  ├─ ② separator 分离
  │      ├─ vocals.wav
  │      └─ accompaniment.wav
  │
  ├─ ③ 使用 reference.wav + target_text
  │      ↓
  │    tts_new.wav
  │
  ├─ ④ 时长/响度处理
  │      ↓
  │    narration_normalized.wav
  │
  ├─ ⑤ narration + accompaniment 混音
  │      ↓
  │    repaired_audio.wav
  │
  └─ ⑥ 与原视频 remux
         ↓
       repaired.mp4
```

## 8. 时长对齐

MiniMax H3 当前常用单段：

```text
5 秒
```

新朗诵不得为了填满 5 秒而拉长或重复。

原则：

- 诗句自然读完即可。
- 其余时间由 BGM + 环境声继续。
- 不重复朗诵。
- 不拖长最后一个字。
- 不改变视频时长。

如果新语音超过视频长度：

优先按顺序处理：

1. 轻微提高语速。
2. 缩短过长停顿。
3. 给出“朗诵超时”提示。

禁止粗暴截断最后一个字。

---

## 9. 背景音乐与环境声保留

优先使用原视频分离得到的 accompaniment。

重新混音时：

### 人声优先级

```text
朗诵 > BGM > 环境声
```

### 默认响度目标

先以相对关系为主，不在 V1 强制死值：

- 人声清楚、靠前。
- BGM 明显低于朗诵。
- 环境声只作为氛围层。
- 不能出现人声被古琴、箫、水声覆盖。

建议最终增加 EBU R128 / LUFS 规范化。

可配置：

```text
narration_gain
background_gain
ducking_enabled
```

支持在朗诵期间对伴奏做轻微 ducking，朗诵结束后自然恢复。

禁止：

- 朗诵停顿时 BGM 消失。
- 诗句读完后音频突然全静音。
- BGM 音量泵动明显。

## 15. GPU 与资源策略

该功能与 MiniMax H3 相比资源较轻，但必须纳入现有 Server Agent / GPU 管理思路。

要求：

1. TTS 和人声分离不要默认抢占 H3 正在使用的全部 GPU。
2. 支持指定 GPU：
   ```text
   AUDIO_REPAIR_CUDA_DEVICE
   ```
3. 如果 CPU 分离速度可接受，可允许 Demucs 走 CPU。
4. TTS 默认只使用单张 4090。
5. 页面应显示：
   ```text
   等待中 / 正在分离 / 正在合成 / 正在混音
   ```
6. 任务失败必须释放显存。

后续可和任务04 / 任务05的 GPU 与模型服务管理模块统一调度。

## 17. 输出校验

生成 repaired.mp4 后自动检查：

### 视频

- 视频流存在。
- 分辨率与原视频一致。
- 帧率与原视频一致。
- 时长与原视频基本一致。
- 不发生意外重新编码导致的明显画质损失。

### 音频

- 音频流存在。
- 无明显爆音。
- 无严重削波。
- 新朗诵完整。
- 不重复。
- 不唱。
- BGM / 环境声存在。
- 朗诵结束后 BGM 仍可继续。

### 文件

- ffprobe 可正常读取。
- MP4 可正常播放。
- 文件大小 > 0。
- 输出路径已登记到项目。

## 18. 《暮江吟》首轮验收

使用本次真实生成的 5 个 MiniMax H3 视频进行验收。

目标：

1. 将用户认为“音色很好”的后两段作为参考来源。
2. 从其中提取干净的男性参考音色。
3. 对出现唱腔的两段重新生成朗诵。
4. 新朗诵必须：
   - 音色明显接近参考段。
   - 为正常朗诵，不是歌唱。
   - 普通话清楚。
   - 每句只读一遍。
   - 有自然情绪起伏。
5. 原视频画面保持不变。
6. 原 BGM / 环境声仍存在。
7. 修复后成品能够直接与其他正常分段拼接。

验收不是仅输出 WAV，必须最终输出可直接使用的 MP4。

> 用户可以把已经生成好的 MiniMax H3 诗词视频拖入 PoemVideo Studio，选中一段满意的男声音色，输入正确诗句，一键把唱腔/不理想人声替换成统一、自然、有感情的普通话朗诵，同时保留原有画面、古风 BGM 和环境声，最终得到可直接发布或拼接的 MP4。
